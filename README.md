# NEXUM NOTE

**為法律考生與法律工作者設計的知識管理筆記工具。**

NEXUM 取自 nexus（連結、樞紐）：這個工具要做的不是收集片段，而是把零散的爭點、學說與
實務見解串成自己的知識系統。所以它不是 HackMD clone，也不是通用筆記 App —— 每一個功能
都要通過同一組問題：能不能提升閱讀效率、能不能提升整理效率、有沒有保住 Markdown 的
可攜性、有沒有增加不必要的複雜度。

編輯體驗以 HackMD 為參考：**Mac 是唯一的編輯環境，手機與 iPad 只用來閱讀**。這個前提貫穿下面所有設計決策。

## 品牌

| 項目 | 決定 |
|---|---|
| 名稱 | NEXUM NOTE。品牌是 NEXUM，NOTE 是產品名，所以文字標把 NEXUM 放大、NOTE 退成副標 |
| 標誌 | 幾何化的 N，兩端各一個節點（[`src/components/logo.tsx`](src/components/logo.tsx)）。**刻意避開書本、法槌、天秤** —— 那是法律模板的長相，不是工具的長相 |
| 語氣 | Premium／Academic／Professional。不用驚嘆號，不催促，不推銷 |
| 方案 | 側邊欄左下角是「NEXUM Scholar Free」的額度卡。**沒有付費方案**，那張卡是自己給自己的額度提醒，連過去的是使用說明而不是購買頁 —— 做一個假的付費入口只會消耗信任 |

## 基礎架構

| 項目 | 決定 |
|---|---|
| 同步方式 | 雲端資料庫 + 部署到 Vercel，任何裝置開網址就能用 |
| 後端服務 | Supabase — Postgres（筆記）、Storage（附件）、Auth（登入）三者共用一個免費方案 |
| 前端框架 | Next.js（App Router），部署零設定，後端邏輯直接寫在 Server Actions |
| 登入方式 | Supabase Auth，單人帳號（Magic Link 或 GitHub OAuth）；架構上仍保留多使用者的可能 |
| 離線行為 | 線上為主，離線唯讀 — 快取已讀過的筆記供離線查看，編輯需要連線 |

## 編輯體驗

| 項目 | 決定 |
|---|---|
| 編輯模式 | **左右分割即時預覽**（HackMD 風格）：左邊純 Markdown 原始語法，右邊渲染結果，兩邊捲動同步 |
| 標題 | 內文第一行的 `# 標題` 自動當作列表顯示名稱；沒寫標題就取前幾個字當預覽 |
| 存檔 | 停止輸入約一秒自動存檔 |
| 版本快照 | 每 10 分鐘留一份，每篇最多 30 份。存的是「存檔前」的內容 — 快照要記錄的是回得去的狀態，存後才留的話把整篇刪光再存，快照裡就只剩空字串。還原前會先把當下內容也存一份，按錯了回得去 |
| 存檔狀態 | 編輯區固定位置顯示「儲存中／已儲存／儲存失敗」，失敗時明顯提示並自動重試。斷線時切換成唯讀並說明原因 |
| 編輯輔助 | 完整工具列（粗體、斜體、清單、連結、圖片、表格、程式碼區塊…）+ 快捷鍵並行 |
| 圖片與附件 | 貼上或拖曳即自動上傳到 Supabase Storage，左邊插入 `![](網址)`、右邊預覽區直接看到圖。上傳中先放佔位文字，完成後換成網址 |
| 圖片壓縮 | 上傳前在瀏覽器端壓縮並轉成 WebP，超過一定尺寸的縮到合理長邊。手機截圖動輒 2–3 MB，不壓的話 1 GB 額度貼幾百張就滿了 |
| 組織方式 | 純標籤，不做資料夾；常用筆記可釘選到列表最上方 |
| 標籤輸入 | **標題下方的 metadata 列**（chip + 自動完成）。標籤存在資料庫欄位，不寫進 Markdown 內文 |
| 刪除 | 軟刪除進垃圾桶可還原，30 天後由排程真的刪掉，附件的 Storage 檔案一併回收（見「垃圾桶的定期清理」） |
| 匯出 | 一鍵把全部筆記匯成 `.md` 檔 + 附件打包下載。免費方案有被砍或漲價的風險，這是資料不被綁死的保險 |

## 介面

**桌機（主力）— 三欄**

```
┌──────────┬────────────────┬─────────────────────────────┐
│ 標籤     │ 筆記列表        │  編輯區                      │
│ ─────    │ ────────       │  ┌───────────┬─────────────┐ │
│ 釘選     │ [搜尋框]        │  │ Markdown  │  預覽        │ │
│ #專案    │ 筆記 A         │  │ 原始語法   │  渲染結果    │ │
│ #讀書    │ 筆記 B         │  │           │             │ │
│ 垃圾桶   │ 筆記 C         │  └───────────┴─────────────┘ │
│          │                │  [標題 + 標籤]  …  [已儲存]  │
└──────────┴────────────────┴─────────────────────────────┘
   可摺疊         可摺疊        兩欄都摺起來 = 專注模式
```

搜尋有兩個入口：筆記列表上方的常駐搜尋框，以及命令面板（搜尋、跳轉、新增筆記、切換主題都從這裡走）。

### 分頁

工作區上方有一列分頁，開過的筆記留在上面，點一下就切回去。說明頁也是一個分頁。

**狀態存在 localStorage，不進資料庫**：開著哪幾篇是「這台機器現在的工作狀態」，不是筆記
本身的資料。存進 Supabase 的話，手機開個唯讀頁面也會去改桌機的分頁列，而且每加一個欄位
都要寫 migration。實作是一個 module 層的小 store 配 `useSyncExternalStore`
（[`src/lib/use-open-tabs.ts`](src/lib/use-open-tabs.ts)），順便換到兩個好處：同一個
瀏覽器開兩個視窗時互相同步，SSR 也不會有 hydration 落差。判斷用的純規則在
[`src/lib/tabs.ts`](src/lib/tabs.ts)，有測試。

| 操作 | 行為 |
|---|---|
| 點筆記 | 已經開著就切過去，沒開過就新增一個分頁 |
| `×` 或中鍵 | 關閉。關掉的是目前這個時，跳去左邊那個；左邊沒有就往右；全關完回列表 |
| 右鍵分頁 | 關閉／關閉其他分頁 |
| 重新整理 | 分頁列還原，目前開著哪一篇由網址決定 |
| 筆記被刪掉 | 分頁自動消失（只在畫面上濾掉，不改寫儲存的內容 —— 列表有筆數上限也有篩選，不能拿它當「這篇不存在了」的證據） |

**未儲存的分頁右邊有一個點。** 編輯區把存檔狀態往上報，分頁列讀它
（[`src/lib/workspace-status.tsx`](src/lib/workspace-status.tsx)），兩邊不需要互相認識。

切換分頁**不會擋著等存檔完成**。切走時編輯器卸載，卸載那一刻會把還沒送出的內容補存
（見「存檔」一節），配上 `updated_at` 樂觀鎖，資料不會掉；反過來做成「存完才准切」則是
每次切換都要等一秒，換來的安全性是同一份。

### 標籤是 metadata，不是內文

標籤從一開始就存在 `note_tags` 關聯表，**沒有寫進 Markdown**。但它原本擺在編輯區底部的
狀態列旁邊，位置暗示它是「附屬於編輯動作的東西」。現在它跟標題排在一起：

```
標題（從內文第一行推導）
標籤 chips
────────────────────
工具列
內容
```

- 標題即時從內文算出來（[`titleFromContent`](src/lib/note-display.ts)），規則跟資料庫的
  generated column 一模一樣 —— 兩邊不一致的話存檔前後標題會跳動，`tests/workspace.test.mjs`
  釘住了這件事
- 預覽區仍會渲染內文的 `# 標題`，所以標題會出現兩次。這是 Markdown-first 工具的必然
  （Bear、Obsidian 也是如此）：標題就是內文的一部分，只是額外在上方顯示一份
- 底部狀態列現在只剩存檔狀態

**側邊欄的標籤可以管理**：右鍵一個標籤 → 重新命名（原地編輯，不跳對話框）或刪除。
刪除只拿掉標籤本身，一篇筆記都不會動（`note_tags` 的外鍵是 `on delete cascade`），
選單上直接把這件事寫出來。

**改名撞到既有名稱時合併而不是報錯**：使用者打出同名的意思本來就是「這兩個是同一件事」，
跳一個「名稱重複」只是把合併的工作丟回去給他手動做。實作是把舊標籤的關聯搬到新的那個
（兩邊都掛過的筆記會撞唯一鍵，那正是要的結果），再刪掉舊的。

### 筆記列表與右鍵選單

列表每一列 68px：標題 14px，修改時間與標籤 12px。**不放摘要** —— 掃列表時要的是
「是哪一篇」，摘要只會讓每一列都長得很像。也不做卡片牆，卡片牆一頁放不了幾篇。

Hover 是底色變化加一點陰影（微浮起），active 用品牌色 highlight 加左側一條內縮的 accent。

右鍵，或滑上去點右上角的 `⋯`，都會開**同一個選單、同一份項目**
（[`src/components/context-menu.tsx`](src/components/context-menu.tsx)）：開啟、釘選／
取消釘選、複製 Markdown、匯出 Markdown、移至垃圾桶（沒有永久刪除，那只在垃圾桶裡做）。

- 選單用 portal 掛到 `body`：列表是 `overflow-y-auto` 的容器，畫在列裡面會被裁掉
- `Esc`、點外面、捲動、改視窗大小都會關閉；關掉後焦點還給原本的元素
- 上下鍵可以在項目間移動
- 複製與匯出在瀏覽器端完成（clipboard 與 Blob 下載），Server Action 只負責把內文送過來 ——
  列表為了輕量本來就不帶完整內文
- 從列表刪別篇筆記不會把你踢出正在編輯的那篇（`trashNote` 的 `goHome` 參數）
- 「新增標籤／編輯標籤」是**同一個項目**（依有沒有標籤換字），做的事都是開啟筆記並把游標
  送進標籤欄。拆成兩個只會讓人先猜要按哪一個。跨頁的焦點靠 sessionStorage 的一次性旗標，
  同一頁則靠事件 —— 只做一條會有一半的情況失效

**桌機預設欄寬**：側邊欄 `clamp(196px, 15vw, 208px)`（收合後 58px）、筆記列表
`clamp(244px, 21vw, 268px)`、主工作區吃剩下的空間。用 clamp 而不是固定值 —— 在 2560 上
導覽不該跟著變胖，在 1280 上也不該把工作區擠死。

**分割是 45 / 55**，右邊多一點：這是法律學習工具，讀比寫原始語法重要一點。目前沒有
拖曳調整寬度的功能，所以也沒有要保留的使用者欄寬設定。兩欄都加 `min-w-0` ——
flex 項目的預設 `min-width` 是 `auto`，少了它，長網址或寬表格會撐開欄位而讓整頁出現
水平捲軸。

**兩欄都限制行寬**：預覽區 `68ch`、編輯區 `74ch`（純寫作模式放寬到 60rem 並連同行號
一起置中）。大螢幕上把整行拉到 1200px 只會讓眼睛從行尾找不回行首 —— 這是教科書與
電子書的行寬慣例。提高資訊密度不等於把東西塞滿。

### 側邊欄

由上而下：品牌區（56px）→ 新增筆記 → 搜尋筆記 → 所有筆記／釘選／使用說明／垃圾桶 →
標籤 → 額度卡 → 設定與收合。導覽項目高 38px、圖示 17px、文字 14px，計數壓到 10px
且更淡 —— 它是參考資訊，不該跟項目名稱競爭。

- **Active 用淡墨藍底加左側一條短 accent，不用邊框** —— 邊框在一整排項目裡會互相干擾，
  底色與左側標記才看得出「現在在這裡」
- **釘選是網址上的篩選（`?pinned=1`）而不是另一條路由**，跟標籤走同一套：可以加書籤，
  也不必為它多開一份列表查詢
- **搜尋框長在列表上方**（那是結果出現的地方），側邊欄那一項只是入口，按下去把游標送過去。
  用一個 window 事件而不是 context —— 兩邊沒有其他要共享的狀態，為了一個 `focus()`
  拉一層 provider 不划算
- **主題、匯出、登出收進「設定」選單**：一週用不到一次的東西不該跟每天要用的導覽搶位置。
  快捷鍵總覽與 Markdown 語法一律不放側邊欄，那些在使用說明頁
- 中段（導覽與標籤）獨立捲動，底部的額度卡與設定 `shrink-0` 永遠看得見

**收合（⌘\ 或底部按鈕）是縮成一條 icon rail，不是整條藏起來**：導覽入口全部留著，滑上去
有 tooltip（計數也寫進 tooltip）。整條消失的話，收合狀態下想切到垃圾桶只能靠記網址。
標籤在收合狀態下不顯示 —— 標籤是名字，用 icon 表達不了，擠成一個字的縮寫只會更難認。

**Next.js 的開發指示器**預設在左下角，正好壓住側邊欄底部那排控制項。它由框架繪製在我們的
React 樹之外，沒辦法放進 sidebar，只能選四個角落，所以在 `next.config.ts` 改成 `bottom-right`。
production build 不會出現它。

### 專注模式

`⌘⇧F` 或標題列的按鈕。收起側邊欄、筆記列表、分頁列，整個視窗留給一篇筆記；
保留標題、標籤、工具列、編輯區、預覽區與存檔狀態。

**收起而不卸載。** 三欄用寬度收到 0 加淡出，DOM 全部留在原地 —— 卸載會丟掉列表的
捲動位置，而且退出時整棵樹重新掛載，編輯器連游標都會重置。因此「退出時回到原本的
工作區」不需要進場拍快照、退場還原：底下的狀態根本沒被動過。唯一有記憶的是大綱，
它兩種模式各記一份（專注模式那份預設關閉），所以退出時自然回到原本的開合狀態。

跟三種檢視模式組合起來是這個工具的核心讀書體驗：

| 組合 | 用途 |
|---|---|
| 專注 + `⌘1` | 純寫作。編輯器置中成一欄（含行號一起置中，行號才不會飄在視窗邊緣） |
| 專注 + `⌘2` | 對照著寫。45 / 55，右邊多一點 |
| 專注 + `⌘3` | 純閱讀。只剩標題、標籤與 68ch 的閱讀欄，上下留白加大 |

**只看預覽時工具列會消失** —— 那時候沒有編輯器可以操作，留著只是一條沒有作用的橫條。

狀態存在 localStorage（跟分頁列同一層級的「這台機器的工作狀態」），重新整理仍然在
專注模式裡。判斷規則在 [`focus-mode.ts`](src/lib/focus-mode.ts)，有測試。

**兩個按鍵細節：**

- `⌘⇧F` 走**捕獲階段**並且 `stopPropagation`。CodeMirror 綁的是 `⌘F`（搜尋），
  但它的按鍵比對有 shift 回退 —— 不攔下來的話按一次會同時開搜尋面板與專注模式。
- `Esc` 相反，走冒泡階段：選單、對話框、tooltip、CodeMirror 的自動完成都比專注模式
  更上層，它們處理過的按鍵帶著 `defaultPrevented` 上來，這時就不動作。按一次 `Esc`
  只該關掉一件事。

### 工具列與 tooltip

工具列高 44px，按鈕 32×32、圖示 16px，分四組用細分隔線斷開：復原／重做 ｜ 標題、粗體、
斜體、螢光筆 ｜ 清單、編號、引用 ｜ 連結、圖片、表格、重點區塊、分隔線 ｜ 更多。

詳細的分組理由與備註框的四種類型見下一節。

**Tooltip 是共用元件**（[`src/components/tooltip.tsx`](src/components/tooltip.tsx)），
工具列與側邊欄的 icon 按鈕都走它，內容是「功能名稱 + 快捷鍵」兩行。取代原本的瀏覽器
`title`：那個沒辦法排版（名稱與快捷鍵擠成一行）、延遲由作業系統決定（Mac 上要等一秒多），
也吃不到主題色。滑鼠停 350ms 才出現（防止移動時整排閃），鍵盤走到就立刻出現，
`Esc` 關掉。`aria-label` 仍然保留 —— tooltip 是滑鼠的輔助，不是無障礙資訊的來源。

### 備註／重點框

法律筆記真正需要標記的是四件事，所以 callout 就只有四種（[`src/lib/callouts.ts`](src/lib/callouts.ts)）：

| 類型 | 語法 | 用途 | 顏色 |
|---|---|---|---|
| 重點 | `> [!KEY]` | 考點與結論 | 金色（品牌第二色，最該被看見的） |
| 實務見解 | `> [!PRACTICE]` | 判決、函釋、通說 | 墨藍（法院的立場） |
| 易錯提醒 | `> [!PITFALL]` | 會扣分的地方 | 紅色 |
| 自我理解 | `> [!INSIGHT]` | 自己的話，不是權威來源 | 綠色 |

`⌘⇧M` 直接插入「重點」，工具列的按鈕展開四選一。選單上寫的是用途而不是語法名稱 ——
那才是使用者當下在想的事。

**這四個是自訂類型，GitHub 不認得**：那邊會退回成一般引用，`[!PRACTICE]` 以文字留在
第一行。這是刻意的取捨 —— 底層仍是 blockquote，不會變成亂碼，而且英文標記在任何工具裡
都讀得懂；若改用 `> [!實務見解]` 這種中文標記，匯出到別的工具反而更難讀。

GitHub 原本的五種（NOTE／TIP／IMPORTANT／WARNING／CAUTION）**繼續支援**：既有筆記還在用，
從 GitHub 或 Obsidian 貼過來的也是這些。

程式碼區塊被移到工具列的「更多」裡。法律筆記幾乎不寫程式碼，卻很常需要圈出考點 ——
第一層的位置應該給後者。

### 編輯區的視覺

CodeMirror 預設長得像 IDE，這裡把它調成「筆記編輯器」：

- **行號縮窄、對比壓到 45%**：它是輔助資訊，不該跟正文搶視線
- **游標所在行幾乎看不見**（3.5% 的墨色）。原本用墨藍 6%，在一整片暖白裡是一條藍帶，很吵
- **Markdown 符號降階**（[`syntax`](src/components/markdown-editor.tsx) 這份 HighlightStyle）：
  `#`、`**`、`==`、`>`、`-` 都退到 `--syntax-mark` 那個暖灰，標題與粗體只靠字重與字色分層，
  **不上彩色** —— 使用者要讀的是後面那句話，不是語法糖
- **字級 15px、行高 1.85**：這裡打的是中文不是程式碼，14px 配 1.75 長時間看會累

### 預覽區的閱讀模式

預覽區不只是把 Markdown 渲染出來，它是**法律教材的閱讀版面**：行寬 68ch、行高 1.8、
襯線體。

中文標題沒有大小寫可以拉開差異，只靠字級的話 h2 與 h3 幾乎分不出來，所以每一級各給一個
額外訊號：h1 下面一條線、h2 前面一段墨藍標記、h3 改用無襯線體、h4 再降一階灰。這樣
「壹 → 一 → （一）」那種深層級才數得出來。巢狀清單換記號（disc → circle → square），
引用改成淡墨藍底 —— 法律筆記裡引用通常是判決或條文原文，要跟自己寫的分析一眼分得開。

節奏上還有幾條：段距 1.05em 配行高 1.8（段跟段看得出斷點但不散開）、標題上緣留 2em
下緣 0.55em（標題屬於它下面那一段，不是浮在中間）、標題緊接標題時不留兩層間距、
表格改用無襯線並縮一階字（那是拿來掃的資料，不是內文）。

**螢光筆與備註框都刻意降飽和**：一篇筆記會出現幾十個重點，飽和度一高整頁就變成廣告傳單。
目標是紙本用好筆劃的重點，不是麥克筆的螢光色；備註框的底色只有 6%，層級靠左邊那條線
與標籤，不靠色塊面積。

### 兩欄捲動同步

分割模式下左右兩欄一起捲（[`scroll-sync.ts`](src/lib/scroll-sync.ts)、
[`use-scroll-sync.ts`](src/lib/use-scroll-sync.ts)）。

**用標題當錨點，不是等比例**：左邊是原始語法、右邊是渲染結果，同一段內容在兩邊的高度
差很多 —— 一張圖左邊只有一行 `![](...)`，右邊佔半個螢幕。等比例捲到後面會差到整段。
兩邊的每個標題各自知道自己在哪個高度，中間線性內插；頭尾各補一個錨點，所以最上面
一定對最上面、捲到底一定對到底。沒有標題的筆記自然退回等比例（只剩那兩個錨點）。

實作上有兩個坑，都踩過：

- **回音要有方向。** 我們捲動目標欄之後它會送出 scroll 事件，那個不能再反推回來。
  第一版用一個不分方向的時間鎖，結果是使用者連續捲動時每 120ms 才同步一次，看起來像卡住。
- **不能信 CodeMirror 的高度表。** `lineBlockAt()` 讀的是它自己維護的 height map，而那張表
  在這個專案裡是錯的：它在主題 CSS 生效前就量過一次，之後沒有校正 —— `documentPadding.top`
  停在 0（實際 28）、`defaultLineHeight` 停在 14（實際約 24），整份文件少算四分之一。
  改用 `coordsAtPos()` 走真實 DOM 量測。代價是沒渲染到的行問不出位置，但捲動同步需要的
  錨點本來就在視窗附近，頭尾兩端由 `mapScroll` 自己補。

### 大綱面板

標題列右邊的大綱按鈕會在工作區右側開一欄可點的章節清單
（[`src/lib/outline.ts`](src/lib/outline.ts)、[`outline-panel.tsx`](src/components/outline-panel.tsx)）。
一篇刑法總論兩三千字、標題五層深，捲動找章節是每天最花時間的動作之一。

**從原始碼解析，不是從渲染結果掃 DOM**：只看編輯的模式下右邊根本沒有預覽區，但那時候
更需要跳章節。代價是解析必須跟 CommonMark 一致 —— 特別是 `#標題`（沒有空白）在標準裡
**不是**標題，大綱收了它會跳到一個看起來不是標題的地方，所以也不收。圍欄程式碼區塊裡的
`# 註解` 同樣排除。

點一項會**同時**移動兩邊：編輯器把游標移到那一行（`revealLine`），預覽區捲到對應的標題。
只做其中一邊的話，分割模式下另一半停在原處反而更難對照。

預覽區的標題錨點用**出現順序**（`nexum-heading-0`、`-1`…）而不是標題文字做 slug：
法律筆記裡「意義」「要件」「實務見解」會重複十幾次，slug 一定撞號，而中文 slug 不是被
轉成拼音就是被清成空字串。順序在同一份內文裡永遠唯一，也正好對得上解析出來的 index。

目前沒有捲動時反白目前章節（scroll spy），也沒有快捷鍵 —— 前者要監聽兩邊的捲動事件，
後者要先確認一組瀏覽器沒佔用的組合鍵。

### 內建使用說明

左側欄有一個固定的「使用說明」入口（`/help`），內容來自
[`src/content/help.md`](src/content/help.md)，由 Server Component 讀檔後用同一套
`MarkdownPreview` 渲染。

**刻意不存進 Supabase**：它是程式的一部分而不是使用者的資料，跟著版本走才對。存成一筆
notes 的話會多出一篇能被刪除、釘選、改名、混進搜尋結果的假筆記，而且每次改文案都要寫
migration。放在 repo 裡則是改完 deploy 就更新，也不佔資料庫額度。

**手機 / iPad（唯讀）— 兩層導覽**

- 第一層筆記列表，點進去第二層全螢幕閱讀，左滑或返回鍵退出。
- 只顯示渲染後的內容，不提供編輯介面，也不載入編輯器套件。
- 可加到主畫面當 PWA 用。

**設計 token**

顏色、字級、圓角、陰影都收在 [`globals.css`](src/app/globals.css) 的 `@theme inline` 裡，
元件只用 token，不寫 `text-[12px]`、`rounded-[3px]` 這種一次性的值。

| 類別 | 內容 |
|---|---|
| 顏色 | 主色墨藍 `--accent`、第二色低飽和金 `--gold`、四層暖白底色。金色只當點綴（額度卡的進度條、品牌標記）—— 面積一大就會變成廉價的「金色會員」感 |
| 字級 | `2xs 10` / `xs 11` / `sm 12` / `base 14` / `lg 15` / `display 28`。刻意壓在五階加一個大標 —— 這是密度很高的工具介面，級距再多只會讓同一種東西在不同畫面長得不一樣。`base` 是介面主字級（側邊欄導覽、筆記標題） |
| 圓角 | `sm 3` / `md 5` / `lg 8`，蓋掉 Tailwind 預設的 4／6px。預設值對這種資訊密度偏圓，看起來像 SaaS 後台 |
| 陰影 | 只有兩個：`shadow-pop`（浮起來的選單）與 `shadow-card`（登入卡片）。介面內的層次靠四層底色做，不靠陰影堆疊 |
| 間距 | 直接用 Tailwind 的 spacing scale，不另造一套 —— 那本來就是一組 token，再包一層只是多一個要記的名字 |
| 動態 | 150–200ms，只有淡入與一小段位移。再長就會擋住操作 —— 這是每天用好幾小時的工具，不是展示頁。全部尊重系統的「減少動態效果」設定 |

字級與圓角是**蓋掉 Tailwind 預設值**而不是新增名字：這樣 `text-sm` 在整個專案裡只有一個
意思，不會出現「有些地方用 token、有些地方用預設」的兩套系統。內文（預覽區）不走這套，
它由 `.markdown-body` 用 em 自己管，因為那裡要的是文章的相對層級而不是介面的固定級距。

**視覺風格**

- 溫暖紙感：偏米黃的底色、襯線字體、較寬的行高，適合長時間閱讀與寫作。
- 深色主題另外調整，不是把淺色直接反相 — 底色用暖調的深棕灰而非純黑，維持同樣的紙感。
- 底色分四層：側邊欄 → 筆記列表 → 頁面 → 編輯區，每層都要看得出差別，不能只靠分隔線撐。
- 主題切換在側邊欄的「設定」選單裡（淺／深／跟隨瀏覽器）。**「跟隨瀏覽器」跟的是瀏覽器的外觀設定，不是作業系統** — Chrome 可以自己設成深色而蓋掉系統設定，這正是需要手動選項的原因。
- 色票用 CSS 的 `light-dark()` 寫成單一來源，不要淺色深色各維護一份。
- 程式碼區塊仍用等寬字體，與內文的襯線字體形成對比。
- 字體只從 Google Fonts 載入拉丁文襯線體（Source Serif 4），中文交給系統內建的 Songti TC。Noto Serif TC 這類 CJK webfont 動輒好幾 MB，對一個個人工具不划算 — 反正 Mac 與 iOS 都內建襯線中文字。

### Tab：兩種縮排單位

**縮排單位看行的種類**（規則在 [`src/lib/indent-rules.ts`](src/lib/indent-rules.ts)）：

| 這一行 | Tab 插入 | 為什麼 |
|---|---|---|
| 清單、待辦、有序清單、空行 | 半形兩格 | 那是 Markdown 語法。換成全形空格就不再是巢狀清單了；空行歸這一類是因為接下來最常打的就是清單標記，`　- 項目` 開頭是全形空格，CommonMark 不當它是清單 |
| 其他（一般段落、中文條列、引用） | **一個全形空格 U+3000** | 那些是純文字 |

跨行選取時**逐行判斷**，所以清單與條列混在一起選也不會縮錯。`Shift+Tab` 一次退一層
（一個全形空格，或一層半形縮排），連續兩個全形空格不會被一次清光。

為什麼純文字要用全形空格：**行首的半形空白在 Markdown 裡是排版指令，不是內容**，
渲染時會被吃掉 —— 編輯區看得到層次，預覽卻是平的。全形空格對 Markdown 與 CSS 都是
普通字元，所以兩邊長得一樣，匯出到 Obsidian、Typora 也一樣看得到縮排
（`tests/markdown.test.mjs` 有對應測試）。

代價是原始碼裡混了看不見的全形空格，而且它在等寬編輯區是兩格寬、在襯線預覽區大約
一個中文字寬，兩邊的縮排量不會完全相等。

**這條規則順帶收掉了 indented code block 的問題。** CommonMark 規定行首四個半形空白
就是程式碼區塊，一旦觸發整段變 literal text，`==螢光標記==` 與 `**粗體**` 全部失效。
以前的做法是「一般段落縮到要滿四格時擋下來並跳出提示」；現在一般段落根本不插半形空白，
Tab 不可能再產生程式碼區塊，那道防線與那個提示 banner 就一起拿掉了。手打或貼進來的
四個空白仍然照標準變成程式碼區塊 —— 那是正確的 Markdown 語意，不該掩蓋。

### 縮排參考線

每一層縮排的起點畫一條淡線（每兩欄一條，跟 `INDENT_UNIT` 同一個值）。中文行沒有空格，
光看縮排量很難數出「這是第幾層」，條列與清單混排時特別明顯。

**用參考線而不是尺標**：尺標只告訴你游標在第幾欄，還是得自己換算層數；參考線直接把子項目
跟它的上一層對齊起來，一眼看得出從屬關係。

實作是 line decoration 加一層 `repeating-linear-gradient` 背景，不是插入元素 ——
背景不進入文件流，游標定位、選取範圍、複製出來的文字都不受影響。一層的寬度靠
`defaultCharacterWidth` 量（編輯區是等寬字體才量得準），所以字體或縮放變了就重畫。

空行自己沒有縮排可言，跟前後最近的非空行借，**取比較淺的那一邊** —— 清單結束後接回
最左邊的段落時，線就在那裡停住，不會多畫一段。tab 照 CommonMark 當四欄，全形空格當兩欄。

### 清單與段落的銜接

CommonMark 對「清單能不能打斷段落」有兩條限制，兩條都很容易踩到：

1. **第一個項目不能是空的。** 剛打完 `1. ` 還沒輸入內容時，那一行仍然是段落文字 ——
   這就是「打 `1.` 預覽沒變成清單」的真正原因。
2. **有序清單只有從 1 開始才能打斷段落。** `2. 甲` 接在段落後面不會變成清單。

兩條都是標準行為（`tests/markdown.test.mjs` 有對應測試）。與其要求使用者背規則，
編輯器在**普通段落後面建立清單時自動補一行空行** —— 那本來就是人手寫 Markdown 會做的事，
補完之後兩條限制都不再適用。

補插的時機有兩個，都跟原本的改動放在**同一個 transaction**，所以 `Cmd+Z` 一次退回：

- 手打清單標記後按空白鍵（`EditorView.inputHandler`）
- 工具列的三個清單按鈕（`toggleLinePrefix`）

上一行若是空行、清單、引用、標題、圍欄或表格就不補 —— 那些本來就是獨立區塊。

Enter 的清單延續、空項目退出清單、Backspace 刪除標記，全部由 CodeMirror 官方的
`markdownKeymap` 處理（`markdown()` 預設就會掛上），沒有自訂實作。

### 中文條列

法律筆記沿用公文的層級慣例 ——「一、（一）、（1）、甲、A」，Markdown 只有 `1.` 一種
有序清單，其餘層級沒有對應語法，所以這一層完全在編輯器處理
（[`src/lib/chinese-list.ts`](src/lib/chinese-list.ts)）：

| 行內容 | 按 Enter 之後 |
|---|---|
| `一、意義` | 新增一行 `二、` |
| `（九）第九點` | 新增一行 `（十）` |
| `十九、甲` | 新增一行 `二十、` |
| `甲、學說` | 新增一行 `乙、` |
| `（1）要件` | 新增一行 `（2）` |
| `A、第一點` | 新增一行 `B、` |
| `三、`（空項目） | 清掉標記，跳出條列 |

四套序列各自有上限，走完就不接手，當一般換行：中文數字到九十九、阿拉伯數字到 99、
天干到「癸」（十項）、英文字母到 Z。兩種標記形式（`X、` 與 `（X）`）都通用，
唯一的例外是阿拉伯數字只認 `（1）`：

- `1、` 不接手 —— 中文本來就這樣寫並列（「3、4 月間」），接手的話誤判太多
- `1.` 那一層是 Markdown 自己的有序清單，本來就會延續

其他規則：

- 行首縮排與標記後的空白會沿用，**含全形空格 U+3000** —— 這也是 Tab 在條列行插入的縮排單位，見上面「Tab：兩種縮排單位」
- 半形括號 `(一)`、`(1)` 不接手，避免誤判程式碼或英文內容
- 遞增時沿用原本的寫法：`（１）` 接 `（２）`（全形）、`a、` 接 `b、`（小寫）
- 天干與字母只認單一個字元，`甲乙、` 或 `AB、` 不算標記
- 游標不在行尾、或有選取範圍時不接手

**產生的是純文字**，不是自訂語法，所以匯出的 `.md` 在任何編輯器裡都跟原本一樣，
Markdown 可攜性不受影響。

**延續時會在上一行尾巴補兩個空白。** 純文字的兩行在 Markdown 眼裡是同一段，預覽會把
`一、意義` 跟 `二、要件` 接成一行；行尾兩個空白是標準的硬換行寫法，比 `<br>` 乾淨，
也不必引進自訂語法。已經有空白就不重複補，全形空格不算數（硬換行只認半形空白）。

實作上這個 keymap 是 `Prec.highest`，才排得到官方 `markdownKeymap`（`Prec.high`）前面；
不是中文條列時回傳 `false` 交還給它，Markdown 清單的行為完全不變。

注意瀏覽器保留了 `Cmd+N`、`Cmd+T`、`Cmd+W`，網頁攔不到，所以「新增筆記」只能走命令面板或畫面上的按鈕，不要指望快捷鍵。

## 垃圾桶的定期清理

丟進垃圾桶超過 30 天的筆記會被真的刪掉，**連同它們在 Storage 的圖片**。

實作是一個 route handler（[`/api/cron/purge`](src/app/api/cron/purge/route.ts)）配 Vercel Cron
（`vercel.json`，每天 04:00）。

**為什麼不用資料庫排程**：migration 裡有一支 `purge_deleted_notes()`，但它只刪得掉資料列 ——
Postgres 碰不到 Storage 上的檔案。附件那幾列會被 `on delete cascade` 帶走，圖片檔卻留在
bucket 裡變成孤兒：沒有任何介面看得到它們，卻一直佔著 1 GB 的免費額度。真正會吃掉額度的
就是那些圖片，所以清理必須在看得到 Storage 的地方做。那支 SQL 函式留著當手動的備援。

**順序**：先抓出過期筆記的 id → 讀出它們的 `storage_path` → 刪檔案 → 最後才刪筆記。
反過來的話關聯已經 cascade 消失，就再也不知道該刪哪些檔案了。檔案刪不掉不會中斷資料列的
清理，錯誤訊息會回在 response 裡。

需要兩個環境變數，**兩個都設了才會運作**（缺哪個就回 503 並說明缺什麼）：

| 變數 | 用途 |
|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | 排程沒有登入的使用者，要略過 RLS 才刪得掉東西。等於資料庫最高權限，只放在 Vercel 的環境變數 |
| `CRON_SECRET` | 端點的通行碼。Vercel Cron 會自動帶 `Authorization: Bearer $CRON_SECRET` |

沒設 `CRON_SECRET` 時端點**一律拒絕**：一個誰都能呼叫的刪除端點比沒有排程還糟。

`/api/cron` 也列進 `proxy.ts` 的 `PUBLIC_PATHS` —— 那不是「公開」的意思，是它用 Bearer token
自己驗證，不需要 session cookie。少了這條，排程請求會被導向登入頁，而 307 在 cron 的紀錄上
看起來還像成功。

## 技術架構

```
瀏覽器 (PWA)  ──►  Next.js on Vercel  ──►  Supabase
   │                (Server Actions)        ├─ Postgres  筆記、標籤、版本
   └─ Service Worker                        ├─ Storage   圖片與附件
      快取已讀筆記（唯讀）                    └─ Auth      登入
```

**搜尋**用 `pg_trgm` 擴充建 GIN 索引，配 `ILIKE` 查詢。**不用** Postgres 內建的 tsvector 全文搜尋 — 它的預設斷詞器不處理中文，會把整句中文當成單一 token，導致搜「資料庫」找不到內容裡的「資料庫設計」。中文斷詞得靠 `zhparser` 之類的擴充，在託管環境上不一定裝得了。trigram 對中文的行為正確，幾千篇筆記的規模也完全不會慢；代價是沒有相關度排序，結果依更新時間排。

**附件**放公開 bucket，檔名用隨機 UUID。網址猜不到，但拿到就看得到 — 個人筆記的圖片通常不敏感，換來的是預覽區直接引用、CDN 快取有效，而且匯出的 `.md` 檔在別的編輯器裡打開圖片照樣顯示（簽名網址會過期，匯出檔就廢了）。**要放真正敏感的東西時別用附件功能。**

其他：

- 資料表以 `user_id` 做列級安全性（RLS），即使目前只有一個帳號也照樣設定，之後要開放他人使用不用改架構。
- 編輯器只在桌機版載入，行動版走另一條輕量的閱讀路徑，避免把整包編輯器塞進手機。
- 存檔時用 `updated_at` 做樂觀鎖。單人也會在 Mac 上開兩個分頁編同一篇，沒有這道防線的話自動存檔會互相蓋掉；偵測到衝突就擋下來並提示，不要默默覆蓋。細節見下一節。
- Supabase 免費方案：500 MB 資料庫、1 GB 儲存空間，個人使用足夠；但專案長時間無活動會被暫停，登入後可恢復，長期使用前要留意。

### 存檔與樂觀鎖

存檔帶著上次拿到的 `updated_at`，`update ... where id = ? and updated_at = ?` 影響列數為 0
就是有人動過。這道防線是對的，但它有兩個很容易踩到的坑，兩個都會變成
「明明只有我一個人在打字，卻一直說被別人改過」：

**一、`updated_at` 的 trigger 是 `for each row`，不管改哪一欄都會前進。** 所以按一下釘選
也算一次 update —— 編輯途中釘選一篇筆記，那個編輯器手上的 token 就過期了，而衝突
**刻意不自動重試**（重試等於拿自己的內容蓋掉對方），於是提示會一直掛著直到重新整理。

**二、存檔沒有排隊的話會撞到自己。** 兩次存檔帶著同一個 `updated_at` 送出去，第二次必然
失敗。本機一次存檔幾十毫秒，看不出來；線上一次要跑 auth、快照檢查、update、revalidate，
加上冷啟動輕鬆超過一秒，於是「打字打到一半按 ⌘S」「一陣一陣地打字」都會撞。切換筆記時
的補存更糟 —— 它會被擋掉，**最後幾個字直接消失**。

所以 [`use-autosave.ts`](src/lib/use-autosave.ts) 做兩件事：

- **一次只跑一個存檔**：在飛的時候不送新的，記下「等它回來再存一次」，那時才拿得到新的
  token。卸載時的補存也接在在飛的那一次後面（ref 在卸載後仍然活著）
- **對不上時先分辨是誰改的**（[`save-conflict.ts`](src/lib/save-conflict.ts)）：讀回資料庫
  現在的內容，如果那正是我們上次成功寫進去的那份，就沒有第二個作者 —— 換上新的 token
  重存一次。內容不一樣才是真衝突，停下來問人。連續自動恢復最多三次，避免有東西一直碰
  那一列時無限重試

這一趟額外的讀取**只在衝突時發生**，平常存檔的成本沒有改變。

## 資料模型

完整定義在 [`supabase/migrations/`](supabase/migrations/)。

```
notes       id, user_id, content, title, pinned,
            created_at, updated_at, deleted_at
tags        id, user_id, name
note_tags   note_id, tag_id
versions    id, note_id, content, created_at
attachments id, note_id, storage_path, filename, size, mime_type, created_at
```

幾個實作上的決定：

- `notes.title` 是 generated column，由資料庫從內文第一行推導（去掉開頭的 `#`），不是另外存一個會跟內文不同步的欄位。標題為空時是 `null`，前端改用內文摘要顯示。
- 標籤用 `note_tags` 關聯表而非 `text[]` 陣列欄位 — 改標籤名只要改一個地方，自動完成也只要查 `tags` 一張表。
- `versions`、`attachments`、`note_tags` 沒有自己的 `user_id`，RLS 一律推導自所屬的筆記，避免兩邊的擁有者資訊不一致。
- `updated_at` 由 trigger 維護，前端傳什麼都會被蓋掉。樂觀鎖靠 `update ... where id = ? and updated_at = ?`，影響列數為 0 就是有衝突。

部署到 Vercel 之後還要設兩個環境變數，垃圾桶的定期清理才會運作（見上面那一節）：
`SUPABASE_SERVICE_ROLE_KEY` 與 `CRON_SECRET`。兩個都是**伺服器端**變數，不要加
`NEXT_PUBLIC_` 前綴。排程本身由 repo 裡的 `vercel.json` 定義，不需要在 Dashboard 設定。

專案結構：

```
src/app/          頁面與 layout
src/components/   UI 元件
src/lib/env.ts    環境變數
src/lib/supabase/ browser / server client 與資料庫型別
src/proxy.ts      session 更新與樂觀導向（Next 16 的 middleware）
supabase/         資料庫 migration
```

技術細節上有兩點跟大部分教學文章不一樣，翻文件時要留意：

- Next.js 16 把 `middleware.ts` 改名為 `proxy.ts`，Supabase 官方範例還是舊寫法。
- Next.js 明確建議 proxy 不要當成唯一的授權關卡，所以頁面與 Server Action 各自還要再呼叫一次 `supabase.auth.getUser()`。

[`tests/markdown.test.mjs`](tests/markdown.test.mjs) 共 53 項，涵蓋：

- 行首四個空白依標準變成程式碼區塊；兩個空白仍是段落

- 四種法律備註框的中文標籤、既有的 GitHub 類型沒被弄壞、不認得的類型退回成引用

- 捲動同步的對應：沒有標題時退回等比例、錨點之間線性內插、捲到底一定對到底、
  重疊的錨點不會除以零
